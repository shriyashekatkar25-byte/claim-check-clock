01 · The decision

How long should a claim live before the row filter checks again?

pinned as a board: problem, change, metric, guardrails, people

Customer problem

An app builder serves 12,000 analysts through one service principal. A custom claim on its token (say region=EMEA) decides which rows each person sees. When someone is offboarded or moved to another team, the old claim keeps working until the token is replaced. Security teams ask: how many rows leak in that gap?

Proposed change

As the PM for claim-based filtering in Unity Catalog, I would ship a recommended default for claim lifetime (TTL) in the app template, paired with an optional push revocation hook that kills a user's token as soon as their entitlement changes.

The hard part: shorter TTLs close the gap but multiply token mints, identity-provider load and refresh errors.

Success metric

P99 time-to-enforce: minutes between an access-removal event and the moment the filter stops serving old rows. Target ≤ 30 min. I use the 99th percentile on purpose: the median is set by the push hook, the tail is set by the TTL.

Adoption follows trust: % of multi-user apps on claim filtering at 90 days.

Guardrails

Removals with ≥1 stale read of sensitive rows≤ 2%
P99 time-to-enforce≤ 30 min
Peak token mints per second (fleet)≤ 25/s
Refresh errors users see per day≤ 20

Stakeholders

  • App builders and data engineers (own the service principal)
  • Security and compliance (own the leak budget)
  • Identity team (owns token mint capacity)
  • Unity Catalog governance PM and eng (own filters and ABAC)
  • Support (absorbs "my dashboard broke" tickets)

04 · The math, from my Monte Carlo course

Inverse CDF: turn one uniform number into any waiting time.

A computer hands you uniform numbers U between 0 and 1. If you want a draw from some other distribution with CDF F, you flip the CDF around: X = F⁻¹(U). Small U values land where F climbs slowly, large ones where it is nearly flat, so the draws pile up exactly where the distribution has its mass.

Waiting times between queries. If an analyst fires queries at rate λ per minute, the gap until the next one is exponential, F(x) = 1 − e^(−λx). Solve for x:

gap = −ln(1 − U) / λ  ≡  −ln(U) / λ

Time left on a token. A removal lands at a random point in a token's life, so the time left is uniform on [0, TTL]: F⁻¹(U) = U·TTL.

Which kind of removal. Offboarding, team move and role downgrade are a finite discrete variable. I split [0,1] into pieces of length 0.25, 0.45 and 0.30 and see which piece U falls in.

When does a refresh first fail? If each mint fails with tiny probability p, the number of mints until the first failure is geometric: ⌈ln U / ln(1 − p)⌉. Jumping straight from failure to failure lets me simulate a million mints a day in about twenty steps.

The product lesson: four inverse-CDF draws per removal give me a full distribution of leak risk, not a single average. The average hides the long uniform tail that only push revocation can cut.

Dots start on the U axis and slide across to the curve, then drop to the waiting time they become. Rate λ follows the "queries per active hour" slider.

05 · How I'd run it on real data

Swap the assumptions for logs.

Table names below are illustrative. The idea: measure the real exposure window from audit-style events, then fit the rates the simulation assumes.

1 · Measure the exposure window (SQL)

-- every access removal, the last token minted before it,
-- and queries served with the old claim after it
WITH removals AS (
  SELECT user_id, changed_at, change_type
  FROM   apm_lab.governance.entitlement_changes
  WHERE  direction = 'remove'
    AND  changed_at >= current_date() - INTERVAL 30 DAYS
),
live_token AS (
  SELECT r.*, t.token_id, t.expires_at
  FROM   removals r
  JOIN   apm_lab.identity.token_mints t
    ON   t.user_id = r.user_id
   AND   r.changed_at BETWEEN t.minted_at AND t.expires_at
)
SELECT change_type,
       percentile_approx(timestampdiff(SECOND, changed_at, expires_at) / 60.0, 0.99) AS p99_window_min,
       avg(CASE WHEN stale_sensitive > 0 THEN 1.0 ELSE 0 END)                     AS stale_sensitive_rate
FROM (
  SELECT l.change_type, l.changed_at, l.expires_at,
         count_if(q.touches_sensitive) AS stale_sensitive
  FROM   live_token l
  LEFT JOIN apm_lab.apps.query_log q
    ON   q.token_id = l.token_id AND q.ts > l.changed_at
  GROUP BY ALL
)
GROUP BY change_type;

2 · Re-run the inverse-CDF simulation with fitted rates (Python)

import numpy as np

rng = np.random.default_rng(102)
lam = spark.table("apm_lab.apps.query_log").groupBy("user_id") \
           .count().toPandas()["count"].mean() / (30 * 8 * 60)   # queries per active minute

def exposure(ttl, n=50_000, push=True, q=0.95, delay_min=10/60):
    u = rng.random((n, 3))
    left = u[:, 0] * ttl                              # uniform inverse CDF
    killed = push & (u[:, 1] < q)
    early = -np.log(u[:, 2]) * delay_min              # exponential inverse CDF
    return np.where(killed, np.minimum(left, early), left)

for ttl in (10, 15, 30, 60):
    w = exposure(ttl)
    p_hit = 1 - np.exp(-lam * 0.32 * w)               # P(at least one sensitive query)
    print(ttl, np.percentile(w, 99).round(1), (0.35 * p_hit).mean().round(4))
